# AtroNexus

Small tools that fill gaps in IFS Cloud. See `IFS Cloud Gap-Bridge Platform Tool Descriptions.md` for what's planned. Built so far: sign-in, IFS connections, and tool 1, the capture page.

| Folder | Stack |
| --- | --- |
| `backend/` | FastAPI, SQLAlchemy (SQLite), JWT auth, managed with [uv](https://docs.astral.sh/uv/) |
| `frontend/` | Next.js 16, Tailwind v4, shadcn/ui, API client generated by Orval |

## Prerequisites

- [uv](https://docs.astral.sh/uv/getting-started/installation/) (it installs the right Python for you)
- Node.js 20 or newer

## Running locally

Run the backend and the frontend in two separate terminals.

### 1. Backend (port 8000)

```powershell
cd backend
copy .env.example .env      # first time only, then set JWT_SECRET and ENCRYPTION_KEY
uv sync
uv run uvicorn app.main:app --reload --port 8000
```

Two values in `.env` have no defaults:

```powershell
# JWT_SECRET: a random string of at least 32 characters
uv run python -c "import secrets; print(secrets.token_urlsafe(48))"

# ENCRYPTION_KEY: encrypts the IFS passwords and client secrets you save
uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Keep `ENCRYPTION_KEY` safe and don't change it: saved IFS credentials can't be decrypted without it.

The first start creates the SQLite database (`atronexus.db`) and a user from `ADMIN_USERNAME` / `ADMIN_PASSWORD` in `.env`. API docs are at http://localhost:8000/docs.

### 2. Frontend (port 3000)

```powershell
cd frontend
copy .env.example .env.local   # first time only; sets API_URL=http://localhost:8000
npm install
npm run dev
```

### 3. Sign in

Open http://localhost:3000 and sign in with the admin user from `backend/.env` (`admin` / `admin123` by default). Change that password before using this anywhere real.

To add a user or reset a password:

```powershell
cd backend
uv run python -m app.cli create-user <username>                      # joins the AtroNexus organization
uv run python -m app.cli create-user <username> --org "Customer Ltd"  # joins (or creates) a customer organization
```

Each customer is an organization and sees only its own connections, capture pages and captures. The admin user from `.env` belongs to the "AtroNexus" organization and is the platform admin.

The database schema is created and upgraded automatically when the backend starts (Alembic, `backend/migrations/`). An existing database from before organizations existed is upgraded in place: its users, connections and capture pages move into the "AtroNexus" organization.

## Accounts and sign-in

- **Sign-up (`/signup`):** anyone can create an account. It creates a new organization (their company) with them as its owner, signs them in, and emails a link to confirm the address. Until they confirm it, they can look around but can't save or test IFS connections or capture pages.
- **Sign-in** uses the email address. Accounts from before email sign-in (like the seeded `admin`) can still use their username; set `ADMIN_EMAIL` to give the admin an email.
- **Forgot password (`/forgot-password`)** emails a reset link that works once, for 1 hour. Resetting signs the user out everywhere else.
- **Emails:** with `EMAIL_BACKEND=console` (the default) nothing is sent; each email, including its link, is printed in the backend log. To send for real, verify a domain at [Resend](https://resend.com) and set `EMAIL_BACKEND=resend`, `RESEND_API_KEY` and `EMAIL_FROM` (an address on that domain). `APP_URL` must be the frontend's public address, because the links in emails point there.

- **Team (`/team`):** owners and admins invite people by email with a role. The invite link works once, for 7 days, and the person picks their name and password. Roles: **owner** (everything, including managing owners), **admin** (connections, capture pages and the team, but not owners), **member** (can look at everything but change nothing). An email that already has an AtroNexus account can't be invited yet: each account belongs to one organization.

How a sign-in works:

1. The login form posts to a Next.js server action, which calls `POST /api/auth/login` on the backend.
2. The backend checks the password (argon2) and returns a JWT.
3. Next.js stores the JWT in an HttpOnly cookie (`atx_session`), so browser JavaScript can't read it.
4. Server components and actions send the token to the backend as `Authorization: Bearer`.
5. Pages other than `/login` redirect to the login page when there's no session. An expired or rejected token clears the cookie.

## Capture page (tool 1)

A button in IFS opens a link to this site. The page reads the user's location, IP address and device, and writes them back to the IFS record.

**Set it up in AtroNexus:**

1. **IFS connections → New connection.** Enter the IFS base URL and a service user. For IFS Cloud, use OAuth2: the token URL (usually `https://<ifs-host>/auth/realms/<realm>/protocol/openid-connect/token`), the client ID and the client secret. Save, then use **Test connection**.
2. **Capture pages → New capture page.** Pick the connection and enter:
   - **IFS endpoint:** the path to the capture request record, with `{request_id}` where the ID goes.
   - **Request body:** JSON with your entity's attribute names and placeholders such as `{latitude}` and `{ip}`. The list of placeholders is on the form. `"{latitude}"` on its own is sent as a number; if the IFS attribute is Text, write `"{latitude:text}"` so it's sent as a string (IFS rejects a number for a Text attribute).
3. Copy the **Link for IFS**. It looks like `https://<this site>/c/<id>/${RequestId}`.

**Set it up in IFS** (not part of this repo yet):

- A custom entity for capture requests, with attributes for the values you send (for example `CfLatitude`, `CfLongitude`, `CfStatus`).
- A custom command on that entity that opens the link above. IFS fills in `${RequestId}` from the record.
- A custom event that copies the values to the real record, or rejects them (for example, when the location is denied or too far away).

**What happens on each capture:**

1. The page asks the browser for the location. If the user refuses, they can try again or continue without a location; IFS then gets `Denied` as the status.
2. The backend signs in to IFS, reads the record to check it exists and to get its ETag, then sends the values with PATCH.
3. Each request ID can be captured once. If IFS rejects the values, the page shows IFS's message and the user can try again.
4. Every attempt shows up under **Capture pages → Recent captures**, with IFS's answer.

Browser locations can be faked, and desktop accuracy can be off by kilometres. Treat the location as convenient evidence, not proof.

## Deploying (Vercel + Northflank)

```
Browser ──HTTPS──▶ Vercel (frontend) ──HTTPS + X-Internal-Key──▶ Northflank (backend) ──▶ IFS
                                                                         │
                                                                   Neon (Postgres)
```

The backend gets its own public address on Northflank, but it refuses every request that doesn't carry the shared `INTERNAL_API_KEY`, so only the Vercel frontend can use it. `/api/health` is the one exception, for Northflank's health check. The frontend passes the browser's IP (which Vercel sets and the browser can't fake) in `X-Client-IP`, and the backend only believes it together with the key.

Both platforms deploy from Git, so commit and push this repo to GitHub first.

### 1. Generate the secrets

Run these locally and keep the output somewhere safe, like a password manager:

```powershell
cd backend
uv run python -c "import secrets; print('JWT_SECRET=' + secrets.token_urlsafe(48))"
uv run python -c "import secrets; print('INTERNAL_API_KEY=' + secrets.token_urlsafe(48))"
uv run python -c "from cryptography.fernet import Fernet; print('ENCRYPTION_KEY=' + Fernet.generate_key().decode())"
```

Use new values, not the ones in your local `.env`. Back up `ENCRYPTION_KEY`: without it, the IFS credentials saved in production can't be decrypted.

### 2. Database on Neon

1. Create a Neon project in the region closest to Northflank (e.g. AWS Asia Pacific, Singapore).
2. On the dashboard, click **Connect** and copy the connection string with **connection pooling on** (the host contains `-pooler`). It looks like:
   ```
   postgresql://user:password@ep-xxxx-pooler.ap-southeast-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
   ```
   Use it as-is for `DATABASE_URL` in the next step. The backend creates its tables on the first start.

Notes:
- The backend turns off psycopg's prepared statements for Postgres, because they can break behind Neon's pooler.
- On the free plan Neon pauses the database when idle. The first request after a pause takes a moment longer while it wakes up.
- Use a separate Neon branch or database for testing. The backend tests drop every table (`TEST_DATABASE_URL`), so never point them at production.

### 3. Backend on Northflank

1. Create a project in the same region as the Neon database.
2. Create a **combined service** (build and deploy) from your GitHub repo:
   - Build type **Dockerfile**, build context `/backend`, Dockerfile `/backend/Dockerfile`.
   - Port **8000**, protocol HTTP, **public**.
   - Health check: HTTP `GET /api/health` on port 8000.
3. Runtime variables (put the secrets in a secret group):

   | Variable | Value |
   | --- | --- |
   | `JWT_SECRET` | from step 1 |
   | `ENCRYPTION_KEY` | from step 1 |
   | `INTERNAL_API_KEY` | from step 1 |
   | `ADMIN_USERNAME` | e.g. `admin` |
   | `ADMIN_PASSWORD` | a strong password (only used to create the user on the first start) |
   | `ADMIN_EMAIL` | optional: your email, so you can sign in with it and reset your password |
   | `DATABASE_URL` | the Neon pooled connection string from step 2 |
   | `APP_URL` | the Vercel address, e.g. `https://atro-nexus.vercel.app` (links in emails point here) |
   | `EMAIL_BACKEND` | `console` until you have a sending domain (emails go to the log), then `resend` |
   | `RESEND_API_KEY`, `EMAIL_FROM` | only with `EMAIL_BACKEND=resend`; `EMAIL_FROM` like `AtroNexus <no-reply@yourdomain.com>` |

4. Deploy, then open `https://<northflank-url>/api/health`. It should answer `{"status":"ok"}`. Any other path should answer `{"detail":"Forbidden"}`, which shows the key check works.

The Dockerfile adds the extra CA certificates in `backend/certs/`, which DSS UAT needs because its server doesn't send its full certificate chain.

### 4. Frontend on Vercel

1. **Add New → Project**, import the repo, and set **Root Directory** to `frontend`. Vercel detects Next.js.
2. Environment variables (Production):

   | Variable | Value |
   | --- | --- |
   | `API_URL` | the Northflank URL, e.g. `https://p01--atronexus-api--xxxx.code.run` (no trailing slash) |
   | `INTERNAL_API_KEY` | the same value as on Northflank |

3. **Settings → Functions → Function Region:** pick the region closest to Northflank and IFS (e.g. Singapore, `sin1`). Each page load calls the backend, and every capture goes Vercel → Northflank → IFS, so distance adds up.
4. Deploy, sign in with `ADMIN_USERNAME` / `ADMIN_PASSWORD`, and set up the IFS connection and capture page again. Production has its own database.
5. Update the IFS custom command to the new **Link for IFS**, which now uses the Vercel address.

### Things to check

- **IFS firewall:** if IFS only accepts certain IP addresses, it has to allow Northflank's outgoing address.
- **Vercel plan:** the free Hobby plan is for non-commercial use only. Use Pro for customer work.
- **Changing the internal key:** set the new value on both platforms, then redeploy both.

## Troubleshooting

- **"Can't reach the server" on the login page:** the backend isn't running, or `API_URL` in `frontend/.env.local` is wrong.
- **Port 3000 or 8000 already in use:** a server from an earlier run is still running. Find it with `Get-NetTCPConnection -LocalPort 3000` (PowerShell) and stop it.
- **Backend fails at startup with a `jwt_secret` or `encryption_key` error:** that value is missing from `backend/.env` or too short. See step 1.
- **"Stored secret can't be decrypted":** `ENCRYPTION_KEY` changed since the connection was saved. Put the old key back, or enter the secret again on the connection.
- **The capture page says "Location only works when this page is opened over HTTPS":** the site was opened over plain HTTP from another machine. `localhost` is fine for testing.
- **Everything fails with "Forbidden" in production:** `INTERNAL_API_KEY` differs between Vercel and Northflank, or one side is missing it. Vercel only picks up changed variables after a redeploy.
- **`CERTIFICATE_VERIFY_FAILED` from a new IFS server in production:** its certificate chain is incomplete. See `backend/certs/README.md`.
